# Society Gate v1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A working visitor-management system for one society — guard app, resident app, web admin panel — on a multi-society data model.

**Architecture:** All business rules live in Postgres (Supabase): tables, Row-Level Security, and `security definer` RPC functions that the apps call. A Supabase Edge Function sends Expo push notifications when a visit is created or a pass is used. One Expo (React Native) app serves guards and residents by role; a Vite + React web app serves society admins. Shared TypeScript constants, types and pure helpers live in a workspace package.

**Tech Stack:** TypeScript, npm workspaces, Supabase (Postgres 15, Auth phone OTP, Storage, Realtime, Edge Functions/Deno, pg_cron, pgTAP), Expo SDK (latest stable) + Expo Router + expo-notifications + expo-image-picker, Vite + React for admin, Vitest, jest-expo + @testing-library/react-native.

**Spec:** `docs/superpowers/specs/2026-11-20-society-gate-design.md`

## Global Constraints

- TypeScript everywhere (owner knows JavaScript).
- Every society-scoped row carries `society_id`; RLS enabled on every table; no table readable across societies.
- Roles: `admin | guard | resident`, held in `memberships` (one person, many roles/societies).
- Visit statuses: `pending | approved | denied | leave_at_gate | expired`. Manual guard outcome: `allowed | sent_back`.
- "Call resident" button appears when a visit is still `pending` 60 seconds after creation.
- A `pending` visit becomes `expired` after 10 minutes with no response.
- First resident response wins; later responses are rejected.
- Pass codes: 6 digits, unique among the society's currently-valid passes; reusable within validity window; revocable; each use creates an `approved` visit linked by `pass_id` and notifies the flat's residents.
- No self-signup: admin (or a resident, for their own flat) creates an invite by phone; first OTP login claims it.
- Phone numbers stored in E.164 (`+91XXXXXXXXXX`). Supabase Auth stores `auth.users.phone` without `+` — compare with `'+' || phone`.
- Online-only; no offline mode. No paid SMS/IVR. English only.
- Android first; iOS from the same code, not published in v1.
- Local dev needs Docker Desktop + Supabase CLI.

## Review Focus

1. **Two residents of one flat tap Approve/Deny at the same moment** → exactly one response is stored; the other sees "Already answered". Test: Task 4 `respond_to_visit` concurrency/second-response test.
2. **Phone typed in different formats** (`98765 43210`, `09876543210`, `+91 98765-43210`) by admin vs OTP login → same person is matched. Test: Task 1 `normalizePhone` cases + Task 3 `claim_invites` test.
3. **Pass code that is expired, not yet valid, revoked, or from another society** → rejected with a specific error, no visit created. Test: Task 5 `use_pass` tests.
4. **Resident responds after the visit expired** → rejected with `visit_expired`; guard can still record a manual outcome. Test: Task 4.
5. **Flat whose residents have no push token** (never opened the app) → guard sees "No one in this flat uses the app — call them" immediately, not after 60 s. Test: Task 1 `shouldShowCallButton` + Task 8 `CallResident` test, using `visit_has_app_users` from Task 4.

### Task 4: Visit RPCs and expiry

**Files:**
- Create: `supabase/migrations/0003_visits_rpc.sql`
- Test: `supabase/tests/visits.test.sql`

**Interfaces:**
- Consumes: Task 3 helpers.
- Produces (all `security definer`, raise `exception` with the message shown):
  - `create_visit(p_flat_id uuid, p_name text, p_phone text, p_purpose visit_purpose, p_photo_path text) returns visits` — caller must be guard of the flat's society (`not_authorized`); `created_by = auth.uid()`.
  - `respond_to_visit(p_visit_id uuid, p_response visit_status) returns visits` — caller resident of flat; `p_response in ('approved','denied','leave_at_gate')` else `invalid_response`; uses `update ... where status='pending' returning`; if no row: `visit_expired` when status is expired, else `already_responded`.

  - `mark_entry(p_visit_id uuid) returns visits`, `mark_exit(p_visit_id uuid) returns visits` — guard only; entry requires status approved/leave_at_gate or manual_outcome = allowed (`not_allowed_in`); exit requires entry (`not_entered`).

  - `visit_has_app_users(p_flat_id uuid) returns boolean` — true if any resident of flat has a push token.
  - `expire_stale_visits() returns int` — sets `expired` where pending and `created_at < now() - interval '10 minutes'`; scheduled with `cron.schedule('expire-visits', '* * * * *', 'select expire_stale_visits()')`.
